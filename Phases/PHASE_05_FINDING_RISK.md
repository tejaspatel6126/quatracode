# PHASE 05 — FINDING & RISK ENGINE

## 1. Phase Overview

**Phase:** 05  
**Name:** Finding & Risk Engine  
**Status:** Planned  
**Depends On:** Phase 04 — Core Security Scanner  
**Next Phase:** Phase 06 — Scan Management & API

---

## 2. Objective

The objective of Phase 05 is to transform the raw security observations
generated by Phase 04 into structured, actionable security findings.

This phase introduces two major components:

1. Finding Engine
2. Risk Engine

The Finding Engine interprets deterministic scanner observations and
creates security findings.

The Risk Engine assigns deterministic severity and calculates an overall
risk score.

---

## 3. Core Principle

The security scanner detects facts.

The Finding Engine interprets those facts.

The Risk Engine calculates risk.

AI does not participate in detection, severity calculation, or scoring.

```text
Phase 04
Raw Observations
      |
      v
Finding Engine
      |
      v
Security Findings
      |
      v
Risk Engine
      |
      v
Risk Score
```

## 7. Finding Engine

The Finding Engine converts scanner observations into security findings.

Example:

```
Observation:
TLS protocol = deprecated

        |
        v

Finding:
Deprecated TLS Protocol

        |
        v

Severity:
High
```

The Finding Engine must use predefined rules.

It must not use AI or probabilistic interpretation.

---

```
    ├── __init__.py

    ├── models.py
```

The exact structure may be adjusted to match the existing architecture.

## 9. Stable Finding IDs

Every finding must have a stable identifier.

Example:

```
TLS_WEAK_PROTOCOL
TLS_CERT_EXPIRED
TLS_CERT_HOSTNAME_MISMATCH
HTTP_HSTS_MISSING
HTTP_CSP_MISSING
HTTP_SECURITY_HEADER_MISSING
HTTP_COOKIE_INSECURE
HTTP_HTTPS_REDIRECT_MISSING
```

These are examples only.

The authoritative IDs must come from:


Finding IDs must not be casually renamed after implementation.

## 13. Finding Titles

Finding titles should be:

- concise
- professional
- understandable
- technically accurate
- stable

Examples:

```
Expired TLS Certificate
Weak TLS Protocol
Missing HSTS Header
Insecure Cookie Configuration
Missing Content Security Policy
```

Avoid sensational wording.

---

## 14. Finding Description

Every finding should contain a deterministic technical description.

Example:

```
The target is using a deprecated TLS protocol version that no longer
provides the recommended level of transport security.
```

Descriptions should explain the technical condition without pretending
to know business impact that was not measured.

---

## 15. Severity Classification

The Finding Engine assigns severity according to documented rules.

Typical levels:

```
CRITICAL
HIGH
MEDIUM
LOW
INFO
```

Exact severity mapping must come from the project's specification.

Do not invent severity values during implementation.

---

## 16. Severity Must Be Deterministic

For the same observation:

```
Observation A
     |
     v
Finding Rule
     |
     v
Severity X
```

The result must always be:

```
Severity X
```

It must not depend on:

- AI
- random values
- current model output
- arbitrary developer judgment
- external LLM responses

---

## 17. Evidence

Every security finding should include evidence showing why it exists.

Examples:

```
Observed:
Strict-Transport-Security header missing
```

or:

```
Observed TLS Protocol:
TLS 1.0
```

Evidence must be concise and security-safe.

---

## 18. Evidence Requirements

Evidence must:

- support the finding
- be reproducible where practical
- avoid secrets
- avoid authentication tokens
- avoid session cookies
- avoid private keys
- avoid unnecessary response bodies

Never store sensitive information simply because it appeared in an
HTTP response.

---

## 19. Remediation

Each finding should map to a deterministic remediation recommendation.

Example:

```
Finding:
Missing HSTS

Remediation:
Configure Strict-Transport-Security for the HTTPS endpoint
with an appropriate max-age according to the deployment policy.
```

Remediation should come from predefined project rules.

AI-generated remediation is NOT part of Phase 05.

---

## 20. Security References

Where appropriate, findings may contain references to recognized standards
or security documentation.

Examples may include:

```
OWASP
RFC
MDN
IETF
```

References should be stable and relevant.

Do not add references that are unrelated to the actual finding.

---

## 21. Finding Deduplication

A single underlying issue should not produce duplicate findings unless
the specification explicitly requires multiple findings.

Example:

```
Same Observation
      |
      +--> Rule A
      +--> Rule A
```

should not produce two identical findings.

Expected:

```
One Observation
      |
      v
One Finding
```

---

## 22. Multiple Evidence Items

One finding may contain multiple supporting observations.

Example:

```
Finding:
Weak Cookie Configuration

Evidence:
- Secure missing
- HttpOnly missing
- SameSite missing
```

The finding engine should combine related evidence when the specification
defines them as one finding.

## 24. Risk Engine

The Risk Engine calculates the overall risk associated with a scan.

It must use deterministic mathematical rules.

Input:

```
Security Findings
```

Output:

```
Risk Score
Risk Level
Score Breakdown
```

---

## 25. Risk Score Principles

The risk score must be:

- deterministic
- reproducible
- bounded
- explainable
- documented
- independent of AI

Same findings must always produce the same score.

---

## 26. Score Range

The score range must be defined centrally.

Example:

```
0 — 100
```

If the project's existing documentation defines another range,
that definition takes priority.

The implementation must not silently change the range.

---

## 27. Severity Weights

The Risk Engine may use predefined severity weights.

Conceptual example:

```
CRITICAL -> highest weight
HIGH     -> high weight
MEDIUM   -> moderate weight
LOW      -> low weight
INFO     -> informational
```

Exact numerical weights must be defined in the project's security/risk
specification.

Do not invent arbitrary weights during implementation.

---

## 28. Risk Calculation

The calculation must be centralized.

```
   |
   v

   v

   |
   v

   |
   v
```

A single function/service should be responsible for the authoritative
calculation.

Example conceptual ranges:


These values are examples only.

Use the officially defined thresholds from the project documentation.

---

## 31. Score Normalization

The score must always remain within the defined range.

Example:

```
Raw Score
    |
    v
Normalization
    |
    v
0 <= Score <= 100
```

Unexpected numbers must not produce negative or greater-than-maximum
scores.

---

## 32. Empty Finding Set

If a scan produces no security findings:

```
Findings = 0
```

the Risk Engine must return the documented minimum/healthy score.

The exact value must follow the project's scoring specification.

---

## 33. Duplicate Findings

Duplicate findings must not artificially inflate the risk score.

Example:

```
Finding A
Finding A
Finding A
```

must either be deduplicated before scoring or explicitly handled by the
defined scoring model.

---

## 34. Informational Findings

Informational observations should not unintentionally increase risk.

If INFO findings have a score contribution, it must be explicitly
documented.

Otherwise they should contribute zero risk.

---

## 35. Risk Score Versioning

Risk calculations may evolve over time.

Therefore the result should record a scoring version.

Example:

```
scoring_version = "1.0"
```

This allows future versions to be distinguished.

Historical scan results should remain explainable.

---

## 36. Finding Rule Versioning

Finding rules may also evolve.

Where useful, record:

```
rule_version
```

This helps maintain reproducibility when rules change in future releases.

## 44. Deterministic Processing

The processing order should be stable.

Example:

```
Observations
     |
     v
Sort / Normalize
     |
     v
Apply Rules
     |
     v
Deduplicate
     |
     v
Calculate Risk
```

Do not depend on dictionary iteration order or external model output
for security decisions.

## 45. Error Handling

Finding Engine errors should be structured.

Examples:

```
UNKNOWN_CHECK_ID
INVALID_OBSERVATION
RULE_NOT_FOUND
INVALID_SEVERITY
DUPLICATE_RULE
INVALID_RISK_INPUT
RISK_CALCULATION_ERROR
```

Unexpected input should fail safely.

---

## 46. Missing Observation Data

Scanner observations may occasionally be incomplete.

Example:

```
TLS handshake successful
Certificate data unavailable
```

The Finding Engine should not crash.

It should either:

- skip rules requiring unavailable data, or
- generate a documented scanner limitation finding.

The exact behavior must follow the project specification.

---

## 47. Confidence

If confidence is included in the project domain model, it must be
deterministically derived from scanner evidence.

Do not use AI confidence scores.

Do not create arbitrary confidence values.

If confidence is not required by the documentation, do not introduce it
unnecessarily.

---

## 48. Security Requirements

The Finding & Risk Engine must:

- remain deterministic
- never execute target content
- never make arbitrary network requests
- never call external URLs for scoring
- never use AI for severity
- never use AI for risk scoring
- never trust user-provided severity
- never accept client-controlled risk scores
- never expose sensitive evidence
- never include credentials in findings

---

## 49. Input Validation

Finding Engine inputs must be validated.

Reject or safely handle:

- unknown check IDs
- unknown severity values
- malformed observations
- invalid numerical values
- negative risk contributions
- unexpected data types
- missing required fields


## 55. Risk Calculation Tests

Test:

- zero findings
- one LOW finding

- one HIGH finding
- one CRITICAL finding
- multiple findings
- duplicate findings
- mixed severities
- maximum score
- minimum score
- score normalization

Use exact expected values from the project's scoring specification.

---

## 56. Risk Boundary Tests

Verify:

```
score >= minimum
score <= maximum
```

Unexpected calculations must never escape the defined range.

---

## 57. Determinism Tests

Run the same finding set multiple times.

Expected:

```
Run 1 -> Score X
Run 2 -> Score X
Run 3 -> Score X
```

The score and finding classification must remain identical.

---

## 58. Property-Based Tests

Where useful, test scoring with generated valid finding combinations.

Verify:

- score remains within bounds
- invalid inputs are rejected
- duplicate handling remains consistent
- deterministic output
- no unexpected exceptions
