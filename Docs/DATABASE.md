# AI-Powered Web Security Configuration Auditor

## Database Design Document

**Version:** 1.0
**Database:** MySQL 8.x
**ORM:** SQLAlchemy
**Status:** Initial / Development Baseline

---

## 1. Database Overview

The application uses MySQL 8.x as the primary relational database.

The database stores:

- Users
- Scan requests
- Scan execution status
- Security findings
- TLS certificate information
- Security header results
- Cookie analysis
- Redirect analysis
- Resource analysis
- AI-generated explanations
- Scan metadata

The database is designed to keep security evidence structured, traceable, and associated with a specific scan.

---

## 2. Database Design Principles

The database follows these principles:

1. Every scan has a unique identifier.
2. Every finding belongs to a specific scan.
3. Scanner evidence is associated with the scan that produced it.
4. Security findings are stored separately from raw scanner data.
5. AI output is associated with the finding or scan that generated it.
6. Foreign keys maintain referential integrity.
7. Indexes are used for frequently queried fields.
8. Sensitive information is minimized.
9. Raw secrets must never be stored.
10. Database access is performed through SQLAlchemy.

## 4. Database Naming Convention

Table names shall use lowercase `snake_case`.

Examples:

- `users`
- `scans`
- `findings`
- `security_headers`
- `ai_reports`

Column names shall also use lowercase `snake_case`.

Examples:

- `created_at`
- `scan_id`
- `severity`
- `risk_score`
- `target_url`

Primary keys shall use: `id`

Foreign keys shall use: `<entity>_id`

Example:

- `scan_id`
- `user_id`
- `finding_id`

- `MEDIUM`
- `LOW`
- `INFO`
- `PASS`

Severity is determined by deterministic security rules.

AI must not independently assign the final severity.

---

## 10. Finding Confidence

Confidence represents how strongly the available evidence supports the finding.

Range: `0.0000` – `1.0000`

Example:

- `1.0000` = Very high confidence
- `0.9000` = High confidence
- `0.7000` = Moderate confidence
- `0.5000` = Low confidence

Confidence must not be confused with severity.

Example:

```
Severity: HIGH
Confidence: 0.98
```

## 18. Relationships

One user can create many scans.

```

```

Foreign key:

```

    REFERENCES users.id
```

Indexes shall be created for frequently queried columns.

Important indexes:

- `users.email`
- `scans.scan_uuid`
- `scans.target_hostname`
- `scans.status`
- `scans.user_id`
- `scans.created_at`
- `findings.scan_id`
- `findings.category`
- `findings.severity`
- `findings.finding_code`
- `security_headers.scan_id`
- `cookies.scan_id`
- `redirects.scan_id`
- `resources.scan_id`
- `resources.hostname`
- `ai_reports.scan_id`

---

## 21. Foreign Key Strategy

Foreign keys shall use `ON DELETE CASCADE` for child records that have no meaning without their parent scan.

Example:

```
Deleting a scan
      |
      +-- findings deleted
      +-- cookies deleted
      +-- headers deleted
      +-- redirects deleted
      +-- resources deleted
      +-- certificate deleted
      +-- AI report deleted
```

User deletion should be handled carefully.

If scan history needs to remain after user deletion, `scans.user_id` should be nullable and use `ON DELETE SET NULL`.

---

## 22. Timestamps

All major entities should include:

- `created_at`
- `updated_at`

Timestamps should be stored consistently.

The backend should preferably operate using UTC internally.

The frontend may convert timestamps to the user's local timezone.

---

## 23. JSON Usage

JSON columns may be used for semi-structured technical evidence.

Examples:

- `certificate.san_entries`
- `certificate.protocol_summary`
- `findings.evidence`
- `ai_reports.recommendations`

JSON should not replace relational structure where data is frequently queried.

For example, finding severity should remain a normal indexed column rather than being stored only inside JSON.

## 25. Sensitive Data Policy

The database must never intentionally store:

- User passwords in plaintext
- API keys
- AI provider secrets
- Authentication tokens
- Private keys
- Browser session contents
- Unnecessary personal information

The scanner should store only information necessary to generate the security assessment.

## 26. Database Security

The application shall follow:

- Least-privilege database user
- Strong database password
- Environment-based credentials
- No credentials in source control
- Parameterized queries through SQLAlchemy
- Restricted database network access
- Regular backups in production
- Database connection pooling
- Connection timeout configuration

Example environment variables:

```
DATABASE_HOST
DATABASE_PORT
DATABASE_NAME
DATABASE_USER
DATABASE_PASSWORD
```

## 29. Initial SQL Schema

The following is a conceptual starting point.

```sql
CREATE DATABASE IF NOT EXISTS web_security_auditor
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

USE web_security_auditor;

CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE scans (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    scan_uuid CHAR(36) NOT NULL UNIQUE,
    user_id BIGINT UNSIGNED NULL,
    target_url VARCHAR(2048) NOT NULL,
    target_hostname VARCHAR(255) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'created',

    security_score DECIMAL(5,2) NULL,
    risk_level VARCHAR(20) NULL,

    total_findings INT UNSIGNED NOT NULL DEFAULT 0,
    critical_count INT UNSIGNED NOT NULL DEFAULT 0,
    high_count INT UNSIGNED NOT NULL DEFAULT 0,
    medium_count INT UNSIGNED NOT NULL DEFAULT 0,
    low_count INT UNSIGNED NOT NULL DEFAULT 0,
    info_count INT UNSIGNED NOT NULL DEFAULT 0,
    passed_count INT UNSIGNED NOT NULL DEFAULT 0,

    started_at DATETIME NULL,
    completed_at DATETIME NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_scans_hostname (target_hostname),
    INDEX idx_scans_status (status),
    INDEX idx_scans_user (user_id),
    INDEX idx_scans_created (created_at),

    CONSTRAINT fk_scans_user
        FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE SET NULL
);

CREATE TABLE findings (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    scan_id BIGINT UNSIGNED NOT NULL,
    finding_code VARCHAR(100) NOT NULL,
    category VARCHAR(50) NOT NULL,
    title VARCHAR(255) NOT NULL,

    hostname_match BOOLEAN NULL,
    self_signed BOOLEAN NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

        FOREIGN KEY (scan_id)
        REFERENCES scans(id)
        ON DELETE CASCADE

CREATE TABLE security_headers (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    scan_id BIGINT UNSIGNED NOT NULL,
    header_name VARCHAR(255) NOT NULL,

    path VARCHAR(255) NULL,
    expires_at DATETIME NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
```

## 30. Database Transaction Strategy

Scan creation should use a controlled transaction.

Example:

```
Create Scan
    |
    v
Commit
    |
    v
Run Scanners
    |
    v
Store Results
    |
    v
Calculate Score
    |
    v
Generate AI Report
    |
    v
Mark Scan Completed
```

Scanner-specific failures should not unnecessarily roll back successful scanner results.

## 31. Data Consistency

The following must always remain consistent:

```
scans.total_findings
        =
COUNT(findings)
```

Similarly:

- `critical_count`
- `high_count`
- `medium_count`
- `low_count`
- `info_count`

must correspond to the actual findings stored for that scan.

The backend should calculate or validate these values rather than trusting frontend input.
